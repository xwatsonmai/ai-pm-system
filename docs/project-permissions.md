# 项目角色、页面权限、操作权限与待办职责

项目内角色由管理员创建、改名、编辑、分配和删除。角色使用稳定 ID；名称只用于显示，叫“管理员”不会获得管理能力。成员可以分配多个角色，页面权限和操作权限分别取并集；未授予的能力默认拒绝。项目创建者只是创建记录，成员关系移除或权限降低后不保留隐式权限。

## 页面与入口

| 页面 key | 范围 |
| --- | --- |
| `overview` | 项目概览与汇总统计 |
| `tasks` | 需求池、需求内容与评审、开发协作 |
| `reviews` | 测试、Bug 验证/退回、复测、上线登记、业务验收与交付证据 |
| `versions` | 版本计划、范围、发布快照和历史 |
| `timeline` | 项目时间线及其 Git 变化 |
| `chat` | 本人的平台 Agent 问答、会话与协查 |
| `code` | 代码与变更及问答中的源码读取工具 |
| `settings` | 项目名称和说明 |
| `git` | Git 仓库、认证、默认分支和 Agent 源码阅读配置 |
| `access` | 项目成员、自定义角色和页面权限 |

页面权限决定可以进入的页面及读取的数据范围；发起行为另由下方操作权限控制。已有的编辑、认领、测试、上线登记和验收继续执行原页面和工作流规则。本次不增加任意字段级配置，也不把“发起权限”当作编辑或验收权限。仅网页人类账号可以测试和验收；MCP 的用户明确确认要求、本人项目范围与认领规则继续生效。

## 操作权限

| 操作 key | 含义 |
| --- | --- |
| `agent.ask` | 启动或重试本人问答；还需有问答页面权限 |
| `analysis.run` | 启动其他人工分析；还需有需求池页面权限 |
| `requirement.create` | 发起需求、追加迭代、发起及确认需求变更；不能通过先建 Bug 再改类型绕过 |
| `bug.create` | 提起独立或关联 Bug；关联 Bug 仍需能够读取真实父需求 |
| `bug.create.linked` | 仅提起关联测试/验收 Bug；不允许独立 Bug 或问答中的独立 Bug 建议 |
| `collaboration.create` | 从本人问答发起只读协查；保留原会话归属和环境范围校验 |

“提起 Bug”包含关联 Bug 能力；“仅提起关联 Bug”用于不应独立建单的测试/验收角色。允许读某页不再自动允许创建，允许创建也不自动开放需求池、版本详情、代码或其他人的会话。

例如，运营角色可以只勾选 `chat` 页面，操作只勾选 `agent.ask`、`bug.create`、`collaboration.create`。该成员可以问答、提交 Bug 和发起协查，不能创建需求、确认旧需求建议、追加需求迭代或通过修改类型把 Bug 变成需求；也不能读取需求池或源码。Bug 提交后保留真实编号和提交结果，工作台留在问答页，不跳到无权读取的详情。需要跟进其他业务页面时，再单独授予对应页面权限。

网页入口按能力显示，但服务端才是授权边界。直接 API、个人 OAuth MCP、历史创建建议、Agent 工具和代办写入均重新检查当前操作权限。平台 Agent 代用户建单时使用持久化的真实发起人授权，不能借后台身份获得更多权限。撤销发起权限后，历史问答仍可按原读取权限查看，但不能据此重新启动无权使用的 Agent 或提交旧建议。

任务详情被需求、验收和版本页共用，因此这些页面均可读取任务；只有验收页可执行测试/验收动作，验收与版本页可登记上线。具有关联 Bug 发起能力的验收人员可以围绕真实可读需求提反馈；服务端查询实际父需求与项目归属，不能靠客户端声明“来自验收页”创建独立需求或独立 Bug。普通需求内容编辑与生命周期操作归需求池，变更事项类型还须满足目标类型的创建权限。

父菜单只分组，不隐含授权。个人 MCP 开通与平台设置继续保留各自的个人/平台边界。平台管理员可以恢复项目角色与成员授权，但不会因此获得该项目的业务页面、业务数据或个人会话。

授权必须在服务端执行，隐藏菜单不构成授权。Web API、对象详情、附件、MCP、待办和消息卡片都校验当前权限。聚合上下文不会把无权限页面的需求正文、版本历史、交付证据或 Git 配置一起返回。需求表单需要的版本选项仅返回轻量名称和标识，不等于版本详情权限。

平台问答和人工发起的需求整理、进度、知识、Bug 分析都以持久化发起人的当前权限读取数据，不能借用后台 Agent 身份绕过页面限制。需求/版本/时间线/源码工具按对应页面授权；后台自动需求评审保留其内部处理权限。普通工具每次调用重新校验；原生源码沙盒运行期间也检查权限，失去运行所属页面或源码权限时停止运行。人工分析记录仅本人可读、停止；没有个人归属的旧分析记录和后台任务仍按原任务页面范围共享。同一员工的网页与个人 OAuth 连接按真实用户身份识别，旧本地 token 保留独立客户端身份。

Agent 保存的分析证据也保留 `origin_run_id`，其可见范围不能超过来源运行；不能通过证据列表、需求详情或项目聚合重新共享私有分析。来源运行的页面权限、员工归属与会话删除状态在每次读取时重新核对，分页总数也先按此过滤。旧 `analysis_<run_id>_<12位调用哈希>` 记录按完整标识关联原运行；找不到来源的旧生成记录默认不再共享。后台系统分析仍在原业务页面范围内共享。

附件下载和引用已有附件 ID 时都按实际绑定对象授权：需求、评审和历史快照附件要求能读对应页面；私有问答附件要求能读该用户的会话。项目成员关系、已知 URL 和原上传者身份都不能绕过绑定后的权限。新上传的未绑定草稿仅上传员工本人可预览，网页与其个人 OAuth 可以互读。已删除会话中的引用仍算绑定，不能退回成公开草稿。

## 待办职责

角色的页面权限、操作权限与待办职责是三个配置。成员的 `responsibilities` 可以选 `product`、`developer`、`tester`，决定评审/开发/测试待办的接收；可以为空。角色名称和角色权限不自动产生待办职责。

任务发起人、实际认领人等原有定向接收规则保留。实际派发还要求接收人能访问处理该待办的页面；不会把一个成员无权读取的任务内容发到其消息卡片。角色、成员或职责变化会通知消息中心重算待办。旧卡片按钮在操作时仍重新校验权限。

没有产品职责的成员创建新需求时，会自动 @ 有产品职责且能访问需求池的成员，提醒其参与评审与确认；产品身份按职责判断，不按角色名称判断。具体触发入口和消息渠道行为见 [待办与消息推送](notifications.md)。

## 保存与 API

角色、成员角色和职责保存在项目 JSON 文档中：`project_roles[].pages` 与 `project_roles[].actions` 分别保存页面和操作授权，`memberships[].roles` 保存角色 ID，`memberships[].responsibilities` 独立保存职责。沿用项目文档存储是为了让角色删除、引用替换、成员关系和最后管理员检查共享一个原子边界。`access_version` 是这份配置的并发版本；SQLite 的 `CommitProjectAccess` 使用条件更新比较它，不能用陈旧页面覆盖新的权限。角色列表在适配器内用 `json_each` 分页，不把 SQLite 查询细节放进应用层。

| 接口 | 行为 |
| --- | --- |
| `GET /api/projects/{id}/access` | 本人 `pages`、`actions`、角色、职责及最新 `version`；管理者还可读取完整角色目录 |
| `GET /api/projects/{id}/roles?page=1&page_size=20&q=...` | 角色分页列表及 `total`、`version`；每页 1–100 条 |
| `POST /api/projects/{id}/roles` | `{name, description, pages, actions, version}` 创建角色 |
| `PUT /api/projects/{id}/roles/{role}` | 相同字段修改角色；`version` 是项目 `access_version` |
| `DELETE /api/projects/{id}/roles/{role}` | `{version, replacement_role_id?}` 删除角色；已分配角色必须指定替代角色 |
| `PUT /api/projects/{id}/members/{user}` | `{roles, responsibilities, version}` 分配成员角色与独立职责 |
| `PATCH /api/projects/{id}/settings` | 只更新 `name`、`description`，可带最新 `version` |
| `PATCH /api/projects/{id}/git` | 只更新仓库、认证、分支与源码阅读配置，可带最新 `version` |

项目至少保留一位有效拥有 `access` 页面的成员。可以重命名或替换默认管理员角色；不能通过改权限、降级成员或删除角色去掉最后一位管理者。被引用的角色删除时，成员角色替换与最后管理员检查在同一原子写入中完成。平台管理员提供恢复入口。

新工作台总是明确发送 `actions` 数组，空数组表示不授予任何发起能力。兼容旧客户端时，创建角色省略该字段会按其旧页面能力初始化；编辑角色省略该字段保留已存操作权限，不会重新推导或抹掉限制。未知或重复的操作 key 会被拒绝。

设置页面分别保存各自字段，避免保存项目资料时覆盖 Git 配置。旧 `PUT /api/projects/{id}` 继续接受已有客户端请求，但按实际改动的字段校验所属页面权限，省略的设置字段保留；不能利用旧接口修改无权操作的另一个设置页面。配置保存也推进 `access_version`，客户端保存后应重新读取能力和版本。

## 迁移与兼容

SQLite schema 15 一次性为旧项目建立四个默认角色，并保留原成员关系。原产品、开发、测试角色继续具有所有原业务页面和项目/Git 配置能力；原管理员额外具有角色与权限页面。迁移不会静默收紧旧成员此前可修改项目和仓库配置的能力。

旧角色对应的待办职责只在迁移时转换一次。明确保存的空职责数组不会在重启后重新从角色推导。旧成员 JSON 的单个 `role` 继续可读；返回保留该兼容字段，同时新客户端使用完整 `roles` 与 `responsibilities`。个人会话、OAuth 授权、用户身份、消息绑定和原业务记录不因这次迁移重建。

SQLite schema 16 再为旧角色建立显式操作权限：需求页保留原需求/Bug 发起及人工分析能力，问答页保留问答和协查能力；只有验收页、没有需求页的旧角色只得到关联 Bug 权限，不因此获得独立建单能力。已明确保存的空操作数组保持为空，重启或修改页面不会将其回填。页面、成员身份、职责、会话和授权不重建。

附件上传者元信息只增加在现有 JSON 中，不增加数据库 schema 迁移。旧附件只要仍被真实需求、评审、会话或版本快照引用，就继续按该对象授权读取。旧个人 MCP 上传已保存的员工授权记录可用于识别未绑定草稿的上传者；既无真实引用、也无可核验上传者的旧孤立草稿会拒绝下载与再次引用，用户需要重新上传。不会按项目成员关系推测、回填未知上传者，也不会删除原附件或业务资料。

**使用操作权限后，最低兼容服务版本是实现 schema 16 操作授权的版本。** schema 15 服务不能执行新的操作限制，更旧服务甚至不理解页面限制；旧写入程序还可能丢掉 `actions` 字段。新增 JSON 字段不代表可以安全地直接回退旧镜像。需要回退时优先部署兼容新权限模型的前一构建或向前修复；确需恢复旧数据库，必须停写、另存当前数据，并使用升级前一致性备份制定完整恢复方案，不能覆盖升级后新增业务记录。

回归覆盖迁移与重启、空职责、角色分页、改名不授权、职责独立、角色引用替换、最后管理者、并发冲突、聚合过滤、旧保存接口、MCP、问答工具、消息接收和只拥有验收页的业务流程。构建与完整回归入口仍为 `make test`。
