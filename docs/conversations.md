# 项目问答会话历史

问答现支持异步环境排查协同：当前运行结束后，协同结果仍可通过后台队列触发原会话追加回答。自动回答使用 `kind=question` 保留原会话权限，使用 `trigger_type=collaboration_result` 区分来源；仅渲染 Agent 消息，不生成用户气泡或新标题。页面在输入草稿期间也会发现新结果，并保留选区、焦点和滚动位置。详情见 [异步协同说明](collaboration.md)。

## 使用行为

- 顶部导航、项目问答页头与输入区保持位置，消息区和历史列表分别滚动，长回复不会将页头滚出窗口，也不会被输入框遮挡。
- 会话行提供重命名和删除按钮（桌面悬停或键盘聚焦显示，移动端直接显示）。手动名称为 1–80 个字，保存后优先于 AI 名称；删除需要确认，取消不影响记录。删除当前会话后进入空白窗口，删除其他会话不会切换当前对话。
- 左侧「我的对话」只展示当前用户在当前项目的问答，按最近发言排序；进行中的会话有状态提示。移动端通过「历史对话」展开列表。
- 点击「新会话」立即显示空白窗口。此操作不请求模型、不创建数据库记录；首次消息提交成功后才产生记录。只有附件的消息也支持创建会话。
- 点击历史会话可查看全部消息并继续追问，保持同一个 Pi 会话上下文，不再截取最近 12 轮。不同会话的输入草稿在当前页面各自保留，草稿不跨刷新保存。
- 首轮使用项目所选模型，通过独立的 Pi SDK 临时会话生成标题。输入仅包括首条用户发言（最多 2,000 字）和附件名称，不包含项目事实、仓库正文或工具。标题生成与回答并行，不进入主对话上下文；后续追问不会再次命名。
- 每个新会话额外产生一次短标题模型请求。命名超时或失败时，列表使用首条消息摘要或附件名称，正常回答仍会保存。未配置项目模型、上传失败或请求未被接受时，不创建空会话。
- 当前会话正在回答时不能重复发送；可以切换到其他会话或开启新会话。切换视图不会把后台回答插入另一个对话，也不会因旧请求返回而跳回原会话。

## 从问答创建需求或 Bug

Agent 在判断出明确的改进目标、功能诉求或疑似 Bug 后，可以主动说明理由并展示创建建议。建议包含类型、标题、整理后的 Markdown、验收建议和相关附件，用户可展开检查即将共享的内容，再点击「创建并交给开发」（Bug）或「创建并评审」（迭代需求）、直接回复「创建吧」，或选择「暂不创建」。普通知识问答不强制转需求；拒绝过的建议不反复提醒。纠正或缩小范围时，Agent 先根据新说明重新整理。

用户明确要求创建且指代清楚、关键细节已确认时，Agent 直接整理并保存，不重复询问。Bug 仍缺关键细节时先在当前对话补充，即使用户说“直接创建”也不能用占位内容建单。Bug 创建成功返回真实编号和详情入口，直接等待开发认领，不打开需求评审。迭代需求创建成功后保留评审入口，Agent 在后台评审，不自动打开独立评审窗口。评审结论在需求池和对话卡片标记「待确认」，导航显示待确认数量。正在编辑的草稿和已有窗口不会被后台创建或评审结果打断。

- `propose_requirement` 保存私人的创建建议，不创建需求；`resolve_requirement_proposal` 仅处理本轮用户明确同意/要求创建或暂不创建的指示。自然语言意图由模型理解，并须引用本轮用户原话；附件、历史 Agent 发言、自动协同回传不是确认。工具权限只对具备项目访问权的本人问答开放。
- 仅选取当前会话中与本问题相关的附件，支持沿用前面轮次的图片/文档；服务端校验会话与项目归属，继续遵守 6 个附件、总计 20 MB 的限制。不复制整个私人会话到项目；共享的是建议中的需求稿和所选附件。
- 建议与处理状态保存在独立的 `requirement_intakes` 表。确认时，创建需求、关联附件、记录需求编号、事件和幂等回执在一个事务中提交。并发确认、按钮与文字确认交错、HTTP 响应丢失后重试都复用同一条需求。
- 问答 Agent 整理的 Bug 必须填写 `bug_details`：发生位置/环境、触发场景或复现信息、实际表现、预期行为、修复范围，并有问题描述和至少一条验收条件。根因不要求预先确认，偶发问题可以明确记录现有证据而不编造复现步骤；`missing_details` 必须为空。服务端在建议和确认两个入口拒绝缺失字段、简单待确认占位和仍有待补充事项的 Bug，旧版未确认建议也要重新整理。已经创建的 Bug 重试仍然幂等，不重置认领；用户确认创建后直接进入 `ready`（待认领），通知开发工作列表，开发认领后进入 `doing`。无需额外确认需求，未验证的根因留待开发排查。建议和创建两个入口均校验内容，避免不完整 Bug 静默落回需求评审。
- 迭代需求先进入 `clarify`（需求评审）。创建时已知的 `missing_details` 随建议持久化并写进共享需求文档，问答必须逐项说明还需对接、尚未进入开发。创建工具回执包含实时事项状态、评审状态、当前问题和下一步；已保存但评审排队/运行/失败都不能回答成“搞定了”。后续以最新评审为准，不把创建时的缺项永久当成未解决。提交成功后才启动独立评审；模型未配置、失败或重启不回滚需求及原始问答。评审消息仍按既有流程先保存再运行，允许自由纠正。关闭/删除原对话不会删除已经共享到需求池的需求。
- 只读协同用于环境排查和证据收集，不能代表修复、实施或开发派单。需要修复时应建议创建 Bug，用户确认后交给开发认领，不能再描述为“转协同排查/实施”。

HTTP：`GET /api/projects/{id}/requirement-intakes` 只列出本人的可见会话建议；`POST /api/requirement-intakes/{id}/resolve` 接受 `action=create|dismiss` 和 `request_id`。其他成员、开发 MCP、已删除会话及跨会话确认均不能代为处理。

验证：`make test` 包含权限、原子性、重复确认、重启及真实 Pi SDK 的工具调用检查；`AI_PM_QA_NODE_MODULES=/path/to/node_modules node internal/web/requirement-intake.browser-check.mjs` 使用临时 SQLite 和本地模型协议 fixture，覆盖主动建议、图文附件、按钮/文字确认、明确创建、拒绝、丢响应恢复、Bug 直接待认领且不触发评审、迭代需求评审失败和 390px 布局。截图和报告写入忽略目录 `test-results/requirement-intake-ui/`，不写入正式项目或调用付费模型。

## 需求池实时查询与轻量上下文

问答每轮默认只注入项目基本信息、当前会话关联事项的编号/状态摘要、最近 20 条创建建议和当前会话附件/协同信息，并带上 `as_of`。已创建建议不重复注入需求正文；未处理建议保留确认所需内容。全项目事项正文、事件和证据不再默认进入问答，其他专项分析运行的上下文保持原有行为。既有 Pi 会话中的历史内容仍保留，不能把旧轮次结果视为最新状态。

问答通过两个只读工具按需查询，项目由当前运行绑定，不能由模型切换：

- `requirement_pool`：返回项目总数、类型/状态分布、类型与状态交叉统计、阻塞数量；支持 `kind`、`status`、`blocked`、`query` 筛选及 `offset`/`limit` 分页（默认 20，上限 50）。`project_counts` 是全项目统计，`matched_total` 是筛选后总数，不能以本页条数代替总数。阻塞是独立标记，不能当作事项状态。关键词按编号、标题、正文和负责人匹配，查重需要核对候选详情。
- `requirement_detail`：返回完整事项、验收条件、负责人/阻塞、最近 20 条事件与 10 条证据（明确截断标记），以及评审问题、最新用户补充、最新评审结论和下一步责任方。评审历史默认最近 10 条，最多 20 条，通过 `review_before=next_before` 查询更早消息。最新状态摘要不随历史分页倒退。
- `project_context` 在问答中按需读取项目基本信息、项目级知识和证据；指定 `task_id` 时附带该事项详情。

`requirement_review.state` 区分 `not_started`（未开始）、`reviewing`（排队/评审中）、`awaiting_input`（等用户补充）、`awaiting_confirmation`（等用户确认需求稿）、`failed`（失败）、`stale`（需按新版本重新评审）、`infeasible`（需调整范围）、`not_required`（当前事项已离开需求评审阶段）。`pending_questions` 只包含当前修订、当前评审轮次仍待处理的问题；新补充尚在评审时不再把旧问题列为未回答。历史 Bug 已进入开发时，旧评审问题不改变事项的真实阶段。

`latest_supplement` 保留最新补充正文、表单回答和附件，确认需求稿的操作不算补充；`supplement_state` 区分未补充、已收到、正在评审、已评审和需要重新评审。存储查询失败会返回错误，不能解释成零需求或无补充。查询时间与补充/事件发生时间分开说明。

问答会明确提示已有需求的补充应在对应需求评审中发送；目前不会把聊天内容自动写入已有评审，也不能声称已经同步。现有用户确认需求稿、版本保护和验收权限不变。

验证包括服务端统计/筛选/分页/权限、补充后状态推进与失败保留、过期评审和历史 Bug、Bug 建单字段校验、创建回执，以及真实 Pi SDK 配合本地模型协议 fixture 的跨轮次实时查询。fixture 验证工具与数据链路，不替代实际模型的开放式回答验收。

## 会话存储与访问

沿用 `storage.Store` 的 Run 存储抽象，在 SQLite 中持久化 `owner_id`、`owner_kind`、`conversation_title` 和 `title_status`。通过 `conversation_id` 将消息分组，无需创建空会话记录或引入新的数据库专属逻辑。Pi 原生会话仍保存在项目数据目录下。

手动标题和删除标记保存在独立的 `Conversation` 文档中，经 `storage.Store` 接口读写。与模型流式保存分开，避免迟到的 AI 标题覆盖人工名称，也防止轮询或后台结果让已删除会话重新出现。删除采用逻辑删除：从运行列表和单条读取中排除、拒绝继续追问，并停止正在进行的回答；本版不物理清理原始运行记录、附件和 Pi 会话文件，也不提供恢复入口。旧版无 `conversation_id` 的问答以运行 ID 管理，同样支持改名和删除。

后端在列表、单条读取、停止、追问和 MCP 查询中校验发起人。其他项目成员不能读取或续接个人问答；项目需求整理、进度分析等公共分析继续按项目权限共享。开发 MCP 创建的问答归属其令牌身份，不与用户个人问答混合。

旧版问答没有作者字段，无法可靠推断个人归属。为保留既有资料，旧记录仅向项目负责人展示，列表标注「历史对话」，使用原始首条消息作为临时名称；不会自动批量调用模型回填名称。已有记录、Pi 会话及项目数据均保留。

## 验证

- Go 测试覆盖用户之间的列表隔离、读取/停止/追问拒绝、旧记录归属、MCP 权限、空消息不创建记录，以及同会话并发请求拒绝。
- 使用真实 Pi SDK 和本地模拟模型验证首轮 AI 命名持久化、标题输入与工具隔离、追问保持同一会话且不重复命名。
- 浏览器在独立临时数据库上验证新会话不创建记录、两会话切换、分会话草稿、追问不重复建会话、刷新恢复、命名接口失败仍完成回答，以及 390px 移动端无横向溢出。
- 测试不使用线上模型密钥，不向正式项目写入验证消息。桌面和移动端截图保存在 `test-results/conversations-desktop.png` 与 `test-results/conversations-mobile.png`（忽略目录）。
- 会话管理补充回归覆盖非法名称、越权改名/删除、跨轮次生效、迟到的模型保存、数据库重开后的持久化、删除中断模型请求与禁止续接。浏览器验证重命名保存、取消删除、确认删除、刷新后不恢复，以及桌面/390px 手机滚动前后页头和输入区坐标保持一致。截图：`test-results/chat-management-desktop.png`、`test-results/chat-management-mobile.png`。
