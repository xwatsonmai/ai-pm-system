# 需求池与混合文档

导航、列表和创建入口统一使用「需求池 / 创建需求」。类型展示为「迭代需求」和「Bug 修复」；API 继续使用 `requirement` / `bug`，现有数据与 MCP 接入无需迁移。

创建和编辑使用宽幅文档工作区：标题与图文正文居左，类型、优先级、验收负责人和验收条件居右。小屏幕下属性接在正文后方，底部保存操作固定可见。正文支持标题、加粗、斜体、删除线、列表、引用、代码块、链接和表格，并提供两类需求的填写模板、预览、撤销和重做。模板插入当前光标位置，切换类型不会替换已有内容。

图片可通过选择、粘贴或拖拽上传，直接插入正文。PDF、DOCX、文本及代码文件上传后插入正文链接，并在附件区集中管理、下载或再次插入。移除附件也移除正文中的对应图片和链接引用；原文件继续保留，以免破坏历史资料。上传复用现有项目附件接口，单文件 10 MB、最多 6 个、总计 20 MB。现有文档提取限制同项目问答（扫描版 PDF 需转换为图片；不支持旧版 DOC 和其他二进制文件）。

## 持久化与兼容

- `Task.description` 保存 Markdown，详情与预览用现有 Marked + DOMPurify 渲染；纯文本需求继续可读。
- `Task.attachments` 保存服务端查得的附件元信息；原始文件与文档提取正文仍存储在 SQLite `attachments` 表。
- 创建、编辑接受 `attachment_ids`，校验附件存在性、项目归属、去重与数量/总大小。编辑时省略或 `null` 保留原附件，显式 `[]` 清空，两种语义的请求指纹不同。
- 附件变更和类型变化计入需求修订，继续使用既有 version 乐观并发控制及验收失效规则。
- 需求整理 / Bug 初诊自动携带关联图片和文档正文，沿用模型视觉能力、文本长度校验；文件内容明确标为资料，不是执行指令。

草稿按「用户 + 项目 + 需求 ID（或新建）」保存到当前浏览器 localStorage，关闭和刷新后恢复。它不是服务器草稿，也不会出现在需求评审队列中。编辑草稿保留原 version，不会悄悄覆盖其他人的新修订；遇到版本冲突，先复制草稿内容，再通过「放弃草稿」读取最新需求。上传和提交期间禁止关闭编辑窗口。保存失败保留内容，网络响应丢失后重试沿用已保存在草稿里的 request_id，避免重复创建。成功保存会清除该草稿。

## 创建后的独立需求评审

Agent 从问答整理并经用户确认创建的 Bug，以及 Bug 初诊工具创建的新 Bug，直接进入 `ready`（待认领），开发认领后进入 `doing`。建单时需提供问题描述和至少一条验收条件，不再重复启动需求评审。历史已创建记录不自动变更状态。

手工创建的需求与 Bug，以及从问答创建的迭代需求，保存成功后直接关闭创建窗口，Agent 在后台评审，不自动打开或弹出窗口。有结论后，需求池列表显示「待确认」，区分「查看问题并补充」与「确认需求稿」，导航显示待确认数量，并支持按「待确认」筛选。打开查看不会清除标志；提交补充后恢复后台评审，确认后进入待认领。失败显示「评审失败」，仍保留内容和重试入口。后台评审中的需求不计入「需要我处理」。用户主动打开独立的「需求评审」窗口后，看到的是一个群聊：产品成员、评审 Agent 和开发代理的发言与操作按时间排列，底部是始终可用的输入框（见下文「群聊界面」）。`clarify` 的界面名称改为「需求评审」，交付后的 `review` 仍是「待验收」，两者互相独立。

- Agent 先复述理解，检查可行性与关键遗漏，把需要产品决定的事整理成话题清单（方向性话题在前），每轮只问一个话题：方向性问题用一句话直接问，不出表单；方向确定后再用 1–3 题的细节表单（text、textarea、radio、select、multiselect）。回复不超过 400 字，较长的依据默认折叠，不写内部编号。以上由服务端在 Agent 提交时校验，不通过的提交退回 Agent 当轮改正。每个问题可带推荐值和理由；只有点击「采用推荐」才填写，不自动视为产品同意。详见 [需求评审群聊化](requirement-review-chat.md)。
- 评审对话记录谁做了什么：每条消息带发言人（`actor`、`actor_id`、`actor_kind`），编辑、拒绝、关闭、重新打开需求，重试或复核评审，以及评审失败，都以系统消息留在对话里；编辑、结束、重新打开与需求写入同一事务。
- 评审面向不懂技术的产品人员：正文、问题、选项与推荐理由使用日常业务语言，必要时先解释并举例。代码、协议或数据库等实现选择由 Agent 核实或开发判断，不要求产品代做技术决定。产品可完全不填表，直接问「这是什么意思」「为什么要问」，或说明「你理解错了」。Agent 应先解释或回应纠正；询问含义与空白表单不代表已选择、同意或确认。解释时可不附表单，或只附一个简化问题，尚未决定的业务细节仍待澄清。
- 单选、多选、下拉选择题下方固定提供「补充说明」，支持文字、粘贴图片和选择图片；也可以不选任何选项，只提交该题说明或截图。文字输入题保留原输入框。逐题说明按原问题消息 ID 与题目 ID 关联，和选项分别保存；历史答卷在原题下回显文字和图片，后续轮次复用题目 ID 不会串内容。草稿含逐题文字、图片引用和幂等发送标识，上传失败保留已有输入。通用附件与本轮逐题图片合计最多 6 个、20 MB，每个文件仍不超过 10 MB。
- 问题中的「关键问题」是提示，不使用浏览器必填校验。产品可部分作答，或完全跳过表单，在底部输入纠正说明。输入框支持粘贴截图、拖拽与选择文件，附件限制与创建需求一致。
- 消息先提交 SQLite，再启动模型；缺少配置、不支持图片、超时、模型返回不完整表单或服务重启都只改变评审状态，不影响已创建需求及已保存消息。失败时可重试评审，不重复追加用户消息。
- 未发送文字、表单选择、附件清单和发送请求标识按用户、项目、需求保存在 localStorage。请求响应丢失时重试使用原请求标识，避免重复消息。关闭对话不会停止正在运行的评审。
- 新补充递增评审轮次，取消尚未完成的旧轮。结果同时绑定轮次和需求修订，旧结果不能覆盖新理解；表单回答使用原消息 ID 关联问题。
- Agent 可以提出完整需求稿和验收条件，但不会直接替换正式需求。产品阅读后点击需求稿卡片里的「确认需求，进入待认领」，才在同一数据库事务内更新需求、评审状态和工作记录。存在未发送草稿时先提示发送。原始需求以及后续修订保留在评审消息中。
- 待认领需求再次补充，或编辑已评审需求的实质内容，会重新进入需求评审。已认领开发、交付验收仍沿用原有修订与验收流程。

### 群聊界面

评审窗口是一个群聊，设计与原型见 [需求评审群聊化](requirement-review-chat.md)。

- **顶部**：标题、状态、修订号、参与成员，以及「需求原文」「关联 N」「查看需求」和「···」菜单（拒绝 / 关闭需求）。话题进度条显示 Agent 的话题清单：已确认的打勾，鼠标停留可看结论；点击话题跳到对应提问。
- **消息**：自己的消息在右侧，其他成员、Agent 和开发代理在左侧，连续发言合并头像。经个人 MCP 代办的消息标「经 Claude 代办」。创建、编辑、重试、复核、失败、确认、驳回、关闭和重新打开都是居中的一行事件，带操作人；需要处理时事件里带按钮（重试评审、重新核对、重新打开、查看变更）。
- **Agent 的一轮**拆成连续气泡：简短回复、可展开的分析依据、关联需求标签，以及最多一个提问。方向性问题直接用文字问，可带快捷回复，点选只会填进输入框；细节表单是消息里的卡片，标「话题 n/m」，在卡片内提交，提交后收起为「某人 已提交」，答案作为该成员的一条消息显示，未填写项明确标注。旧版无话题的表单按原样显示。超过 600 字的旧回复和成员长消息默认折叠。
- **需求稿卡片**带版本号（v1、v2…）和验收条件，全文默认折叠，「确认需求，进入待认领」就在卡片里。新稿出现后旧稿标「已被 vN 替代」；需求被编辑后、新一轮复核完成前，旧稿不可确认。测试 Bug 的驳回建议同样以卡片给出「同意驳回，关闭 Bug」。
- **评审进度**：Agent 评审时，「Agent 正在评审」气泡下显示它正在做什么（查找相关需求、阅读「某条需求」、阅读代码、整理回复等）和最近完成的几步。每次工具调用在服务端记录一句可读说明，评审读取接口在运行中返回最近 8 步（`progress`），工具完成即保存，不等模型下一次输出。回复正文仍在整轮提交后显示，不逐字流式输出。
- **需求原文**默认收起，在右侧抽屉中查看；1240px 以上的屏幕与对话并排。抽屉显示当前原文、附件、验收条件和已确认话题的结论，也可查看某一版快照或编辑前后的逐行差异。导入正文中误保存的字面量换行符按文档结构修复显示，不改写已保存原文。
- **输入框**始终可用（需求结束或流程只读时变为只读并说明原因）。当前表单里已有填写时，发送会连同表单一起提交，并在输入框上方提示；存在未发送内容或待复核时，确认按钮不可用并说明原因。上次发送结果不确定时，发送按钮变为「重试保存」，沿用原请求标识。

已提交答卷按服务端消息的 `reply_to` 对应原问题消息，重复使用的问题 ID 不会跨轮串答案；服务端答案不依赖浏览器草稿。新补充、纠正或重新评审会将旧表单设为过期，Agent 也可通过 `expire_form_ids` 指定；过期卡片收起为一行原因，展开只读，未发送的本地草稿仅供查看，不再自动发送或阻挡确认。服务端拒绝提交过期、已提交或原需求修订已变化的表单。

前端按用户、项目、需求保存草稿与幂等请求标识；发送中可关闭重开恢复，保存失败不清空输入。轮询按消息逐条更新，保留正在填写的控件、焦点和展开状态；纯后台更新不会打断历史阅读，用户主动发送后跟随新回复。确认仅针对当前评审轮次，不会自动执行或替代人工确认。需求池通过轻量评审摘要同步后台状态，无数据库迁移。

项目 context 对人类身份附带当前项目的轻量 `requirement_reviews` 摘要（任务编号、修订和状态），列表轮询不加载评审正文、原始文档或答案。标志只采用当前需求修订、仍处于 `clarify` 阶段的结论；旧轮结果不能恢复过期提示。

评审 API：`GET /api/tasks/{id}/requirement-review` 读取记录，`POST` 接受 `action: start | message | retry | confirm` 与 `request_id`。消息另带 `body`、`reply_to`、`answers`（问题 ID 到字符串数组）、`question_notes`（问题 ID 到 `{body, attachment_ids}`，独立于选项）、`attachment_ids`；确认带当前 `generation`。读取沿用项目访问范围，补充及确认由工作台用户或用户明确授权的个人 OAuth MCP 执行；平台仅可启动评审。独立 `requirement_reviews` 表通过版本比较保存记录；`receipts` 保证请求幂等。Pi SDK 使用只读上下文与仓库工具，`submit_requirement_review` 结构化工具仅提交建议，实际确认仍由应用处理。

逐题说明随用户评审消息持久化在现有 JSON 中，无数据库结构迁移。读取时 `question_notes` 各题返回 `{body, attachments}`，附件由服务端按项目归属解析，仅支持图片。Agent 的评审快照包含原题、选择与说明，并将逐题图片加入实际模型图片输入；图片能力不足或模型失败仍保留已保存内容。

### 项目内串行评审与按需上下文

同项目每次只运行一轮 Agent 评审；不同项目独立。创建、修改、补充和重试先持久保存为 `queued`，按 `queued_at` 顺序调度。同一需求排队期间的连续补充合并为最新一轮；运行中收到纠正时取消旧轮，最新一轮重新排队。输出问题、建议稿或失败结果后释放项目名额，等待人工补充和确认不会阻塞其他需求。排队时间不计入模型执行时限。服务重启后恢复尚未执行的队列；已中断的运行保留输入并提示重试。

每条需求保留独立的 `conversation_id`，续接 Pi 会话。默认输入为当前需求的业务范围、验收条件、必要附件以及有分页的项目需求概览，不注入项目历史进度分析、全部需求正文或开发上线回执。续轮只追加新消息、变更的需求原文和新附件。首次迁入的旧评审提供最近十条记录，明确告知还有历史可查；旧记录继续完整保存在 SQLite。迭代需求保留前轮已验收的业务范围、验收结论和原始附件。

Agent 先查看概览，通过 `requirement_pool` 分页/关键词寻找相关需求，再用 `requirement_detail` 阅读其正文、当前评审、用户决定和分页历史。详情增加 `view: review | full`，需求评审默认使用 `review`，需要开发测试或上线回执时显式请求 `full`。每轮输出可附 `relations`，逐项记录关联需求、`overlap | dependency | conflict` 和具体依据；关联对象必须在本轮通过详情工具实际读取。双方界面均可查看当前关联判断并跳转，过期轮次的关系不作为当前结论。

评审保存项目业务范围摘要校验值，以及实际阅读的相关需求修订和评审版本。新增需求、其他需求范围变化或结束、参考过的评审更新，会要求在确认前重新核查；开发进度变化本身不使产品评审失效。后续评审发现冲突时，也会在被关联需求中提示。服务端确认时重新检查，避免旧稿绕过复核；不会自动改写、合并、关闭或回退其他需求。旧评审缺少校验依据时保留原有兼容行为，新的显式冲突仍会提示。

上下文摘要与压缩使用 Pi SDK。自定义模型可配置 `context_window`、`max_tokens`；未填写时兼容原有默认窗口 128000，最大输出最多 8192，并为较小窗口保留合理空间。压缩开始、完成、失败记录在运行中，界面显示整理状态和失败原因。暂时的模型错误先交给 SDK 重试/恢复，最终仍被长度限制截断时明确报错。压缩只改变后续模型上下文，原始会话与用户记录继续保留。

除上方检查外，运行评审浏览器验收：

```sh
AI_PM_QA_NODE_MODULES=/path/to/node_modules node internal/web/requirement-review.browser-check.mjs
```

此检查使用真实页面、HTTP、SQLite 和本地确定性的 Pi 协议测试替身，覆盖方向问题与快捷回复、先解释再提问、每张表单一个话题、五类控件、部分回答与剩余追问、编辑事件与差异、旧稿失效后复核、卡片内确认、旧轮取消、长文本/文档、失败与重试事件、丢失响应、菜单关闭与未发送草稿、关联需求复核、原文抽屉与多种屏幕布局。截图及报告保存于 `test-results/requirement-review-ui/`。Go 的 `TestPiRequirementReviewStructuredConversation` 另外使用真实 Pi SDK 和本地模型接口验证结构化工具调用及多轮上下文；无付费外部模型调用。

## 开发完成、测试与上线

完整流程为：创建保存 → 需求评审 → 待认领 → 处理中 → 测试中 → 待上线 → 待验收 → 已验收。

测试发现问题时从需求提起关联 Bug，需求进入待修复；关联 Bug 全部由产品验证解决或明确关闭后，需求进入待复测，产品开始复测并通过后才能上线。Agent 按需求开发分支的固定提测提交评审 Bug，问题成立自动待认领，细节不足继续问答，驳回须产品确认。见 [需求测试与关联 Bug](testing-bugs.md)。

确认实际上线仍只登记事实，不执行部署。上线记录绑定当前修订与提交 SHA；业务验收使用已登记环境。通用测试或部署证据只保存材料，不自动推进阶段。历史待上线、已上线和已验收事项保留原状态，不补造测试证据。

## 各阶段拒绝、关闭与重新打开

`clarify / ready / doing / pending_release / review` 五个尚未结束的阶段均可由产品选择「拒绝需求」或「关闭需求」，必须填写原因。前者进入 `rejected`（已拒绝），后者进入 `closed`（已关闭）。`done` 已验收是完成状态，不再作为推进中的需求。旧 `canceled`（已取消）记录兼容保留。验收的「退回修改」仍使用 `reject` 操作回到处理中；业务上的「拒绝需求」使用独立 `decline` 操作，结束推进。

需求详情和独立评审提供结束入口。结束记录包含原阶段、原因、操作人和时间；原文、附件、评审答卷、开发提交、上线和验收记录保留。结束后从概览推进数、需要处理列表和开发 `work_list` 中移除，认领凭据撤销，旧开发请求收到已结束提示。平台只停止自身该需求的分析/评审；外部开发 Agent 需要通过工作列表变化通知或重新读取任务获知结束，不声称已终止外部进程。

结束状态和评审只读标记在同一数据库事务保存，晚到的评审结果/消息/确认不能恢复需求。评审保留未发送的本地文字、表单和图片草稿，关闭后不能继续提交；关闭/拒绝原因表单也会暂存，网络响应丢失时用同一请求标识重试。编辑结束需求不会自动重开。

产品可填写原因「重新打开需求」，通过 `reopen` 操作回到需求评审，生成新的修订，原认领凭据失效。历史交付证据保留，不能沿用旧版本直接上线或验收；旧关闭/拒绝记录保留在事项事件中。结束/重开由用户决定：可在工作台操作，也可在对话中明确要求后，经个人 OAuth MCP 的 `task_decline / task_close / task_reopen` 代办。MCP 必须提供原因、用户原话、明确确认标识和最新 `version`；授权声明、实际 OAuth 员工身份及原因与状态、历史、回执一起保存。平台 Agent 仍不能自行决定结束/重开；普通开发 actions 不能绕过该授权入口。

HTTP 继续使用 `POST /api/tasks/{id}/actions`，新增 `close / decline / reopen`，传 `body` 原因、最新 `version` 和唯一 `request_id`。需求新增可选 `resolution` 元数据（`from_status / reason / actor / at`），无数据库结构迁移；状态筛选、问答统计及下一步说明支持 `closed / rejected`。

## 当前里程碑

每条需求和 Bug 必须归属里程碑，创建时自动归入当前版本，没有则在保存原文的同一事务创建。当前只开放一个进行中的里程碑，结束前可以持续追加，一次上线不会结束或冻结范围。需求池按里程碑分组和筛选，历史范围与每次上线快照保留。产品 MCP 支持创建、局部更新、上传附件、自由补充评审与明确确认；必须有用户明确要求和个人 OAuth 身份。规则见 [当前里程碑与时间线](project-versions.md) 和 [MCP](developer-mcp.md)。

## 追加迭代

已验收需求支持追加独立迭代，保留上一轮的已验收快照及最初需求基线，原需求和旧版本不变。新迭代进入当前里程碑并重新评审，已验收后可继续迭代，不限轮数。详见 [追加迭代](requirement-iterations.md)。


### 开发对齐

需求开发中，原开发 MCP 客户端可以提交疑问说明与可选表单，进入「待对齐」。需求池和导航提示产品处理，详情提供「回复开发对齐」。沿用评审的五类控件、推荐提示、逐题说明、图片与附件、草稿及幂等发送，保留始终可用的自由输入框；产品可只回答部分问题，或完全跳过表单纠正开发理解。

产品点击「提交回复，交给开发确认」后，需求进入「待领取」，仅原客户端可继续。产品仍可追加文字说明。开发客户端阅读全部最新回复，认为可以继续后，通过 MCP 确认对齐完成并恢复「处理中」；仍有疑问时再次提交问题，回到「待对齐」。产品提交回复不会自动完成对齐，不启动平台 Agent 代为判断。

原客户端无法继续时，产品可以从已回复需求的详情点击「重新开放领取」。全部尚未追加的开发对齐问题、产品答复、纠正和附件引用会追加进正式需求的「需求评审对齐补充」，解除客户端限制并撤销原认领凭据，允许其他客户端读取完整上下文后认领。已有需求评审、交付、上线及验收历史保留。

状态路径：处理中 → 待对齐 → 待领取（仅原客户端）→ 开发客户端确认 → 处理中。兜底路径：待领取（仅原客户端）→ 产品重新开放领取 → 待领取（开放领取）。
