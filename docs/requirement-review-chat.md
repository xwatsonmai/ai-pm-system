# 需求评审群聊化：消息类型与 Agent 提问规则（设计稿）

状态：阶段 1（后端：留痕、提问规则、服务端校验）与阶段 2（群聊界面，含开发对齐和测试 Bug 评审）均已实现。本文是两个阶段的共同依据；实现时如有调整，先改本文。

## 为什么改

现有评审窗口按文档组织：左侧原文，右侧长分析、嵌入式问题卡片、关联需求、需求稿、提示横幅和底部流程操作区同时出现。Agent 一轮最多可提 8 个问题，正文可长达 10 万字，复述、可行性、关联需求和待确认差异混在同一条消息里，还出现过把内部编号直接写给产品的情况。多人协作时，创建、编辑、重试、关闭等操作不进对话，表单回答折叠在原问题下，看不出是谁在什么时候做了什么。

改造后的原则：

1. **一个需求就是一个群聊。** 产品成员、平台 Agent、开发代理都是群成员，谁说了什么、做了什么都是一条消息。
2. **一次只谈一个话题。** Agent 先列话题清单，方向性问题先用文字问，方向定了再用小表单问细节，每张表单最多 3 题。
3. **操作跟着消息走。** 重试、复核、确认这些按钮放在对应消息里，不再常驻在窗口底部或顶部横幅。

## 群成员

| 成员 | `actor_kind` | 显示 |
|---|---|---|
| 产品成员 | `human` | 姓名。当前登录人的消息在右侧，其他人在左侧 |
| 产品成员经个人 MCP 代办 | `human`，且消息带 `authorization` | 姓名 + 「经 Claude 代办」标记 |
| 平台 Agent | `platform` | 「评审 Agent」 |
| 开发代理（开发对齐） | `dev_agent` | 开发 MCP 客户端名称，例如「开发代理 · Cursor」 |

消息新增 `actor_id` 与 `actor_kind`。左右位置按 `actor_id` 与当前用户比较决定，不按名字比较。历史消息只有 `actor` 名字，统一显示在左侧。经个人 MCP 代办的消息记在本人名下（`actor_id` 为员工 ID，名字去掉「 · MCP」后缀），并保留 `authorization`。

需求新增 `creator`（`id / name / kind`），创建、追加迭代、从问答创建时记录。评审读取接口返回派生字段 `creator`；旧需求没有记录时，取该需求第一条工作记录的操作人名字（没有 `id`）。发给模型的输入只保留名字，不含账号 ID。

## 消息类型

存储仍是 `RequirementReview.messages` 一个数组，JSON 存储不需要迁移。`role` 保持 `user / assistant / system`，界面按下表拆成气泡。

| 类型 | 存储 | 界面 |
|---|---|---|
| 系统事件 | `role=system`，`action` 为事件类型，`event` 存补充数据，`body` 是完整一句话 | 居中灰字一行：谁 · 做了什么 · 时间；需要操作时带一个按钮 |
| 成员发言 | `role=user, action=message`，只有 `body` / 附件 | 普通气泡 |
| 提交表单 | `role=user, action=message`，带 `reply_to` 与 `answers` / `question_notes` | 气泡标题「提交了话题 n · 标题」，下面逐题列答案摘要，附加文字在后 |
| Agent 一轮回复 | `role=assistant`，`result` 为 v2 结果 | 同一发送者的连续气泡：回复 → 可折叠分析 → 关联需求标签 → 提问 → 需求稿卡片 |
| 方向性提问 | `result.ask.kind=direction` | 气泡里一句问题 + 可选快捷回复；直接在输入框回答 |
| 细节表单 | `result.ask.kind=form` | 气泡里的表单卡片，标题「话题 n/m · 标题」，1–3 题，卡片内提交 |
| 需求稿 | `result.proposal` | 卡片：版本、验收条件条数、查看全文、确认按钮 |
| 开发对齐提问 | `role=assistant, action=request_alignment` | 开发代理的气泡，表单规则同细节表单 |

Agent 的一轮仍存为一条消息（`rm_<run_id>`），只是界面拆成多个连续气泡，像 IM 里同一个人连发几条。

### 系统事件清单

| `action` | 文案示例 | 按钮 | 写入时机 |
|---|---|---|---|
| 需求创建 | 林悦 创建了需求 | 查看原文 | 不存为消息：界面用评审读取结果的 `creator` 和需求的 `created_at` 显示在最前 |
| `task_edited` | 周航 编辑了需求（R1 → R2） | 查看变更 | 编辑保存时与需求修订同一事务写入，附提交后的需求快照，并让当前表单过期。下一轮评审不再补「需求内容已保存」消息 |
| `review_retried` | 林悦 重新发起了评审 | — | `retry` 操作 |
| `recheck_requested` | 林悦 请 Agent 重新核对关联需求 | — | 当前结论需要复核时的 `retry` |
| `review_failed` | 评审没有完成：模型响应超时 | 重试评审 | 每次评审失败（含无法启动、服务重启中断），原因在 `event.reason` |
| `recheck_needed` | 需求「模板积分」有修改。确认前需要重新核查与本需求的交叉与冲突。 | 重新核对 | 读取时计算，不落库，总是显示在最新位置。点名变化的需求：新增、修改、结束、重新打开；其他需求的评审发现冲突，或评审参考的需求有修改、新评审时同样点名。需求稿的确认按钮锁住，旁边提示「其他需求有变化，点下方「重新核对」后再确认」 |
| `confirm`（`role=user`） | 林悦 确认了需求稿 v2，需求进入待认领 | 查看需求 | 沿用现有用户消息和 action，界面按事件显示 |
| `confirm_rejection`（`role=user`） | 林悦 同意驳回，Bug 已关闭 | — | 沿用现有用户消息和 action，界面按事件显示 |
| `task_closed` / `task_declined` / `task_canceled` | 周航 关闭了需求：并入「模板积分」一起做 | 查看原因 | 与结束状态同一事务写入，原因在 `event.reason`，当前表单过期 |
| `task_reopened` | 林悦 重新打开了需求：恢复独立排期 | — | 与重新打开同一事务写入，附新修订的快照 |
| `alignment_completed` / `reopen_claim` | 沿用现有文案 | — | 沿用 |

事件的补充数据放在消息的 `event` 对象里，字段按需取用：

```json
{"from_revision": 1, "to_revision": 2, "reason": "并入「模板积分」一起做"}
```

需求的编辑、结束和重新打开都经过同一个任务提交事务：应用层把要追加的消息作为 `RequirementReviewNote` 随工作记录传给存储层，存储层在写需求的同一事务里把它追加到已有的评审记录。没有评审记录的需求不受影响。

### 关联需求

本需求指向别人的（`result.relations`）和别人指向本需求的（`incoming_relations`）都不再占消息正文或横幅：

- Agent 回复下方显示一排标签「关联：模板积分 · 范围重叠」，点开看一句话依据。
- 顶部「关联 2」按钮列出双向关联，带跳转。
- 关联变化需要复核时，显示上面的 `recheck_needed` 事件。每轮评审开始时记录项目里其他需求的范围摘要（每条一个短摘要），据此判断哪条需求变了；之前的评审只记了整体指纹，只能显示笼统的提示。

## `submit_requirement_review` v2

```jsonc
{
  "reply": "string，必填，≤400 字。先说结论或变化，再引出本轮的问题",
  "analysis": "string，可选。较长的依据与推理，默认折叠",
  "decision": "clarify | ready | infeasible | reject_bug",
  "agenda": [
    {
      "id": "pricing_mode",
      "title": "≤20 字的话题名，例如「改价方式」",
      "kind": "direction | detail",
      "status": "open | resolved | dropped",
      "conclusion": "resolved 时必填，一句话结论"
    }
  ],
  "ask": {
    "topic_id": "必须是 agenda 中 status=open 的话题",
    "kind": "direction | form",
    "question": "direction 必填：一句话问题",
    "quick_replies": ["direction 可选，≤3 条，每条 ≤30 字"],
    "questions": ["form 必填，1–3 题，结构同现有 RequirementQuestion"]
  },
  "relations": ["沿用现有结构"],
  "proposal": {"description": "...", "acceptance": ["..."]},
  "expire_form_ids": ["沿用"]
}
```

存储映射：`reply` 存入现有 `body`（消息正文继续使用 `body`），`ask.questions` 存入现有 `questions`，`ask` 的其余字段存入 `result.ask`（表单时只有 `kind` 和 `topic_id`）。这样回答关联（`reply_to`）、逐题说明、表单过期这些已验证的逻辑不用重写。`agenda` 每轮完整提交，服务端另存一份到 `RequirementReview.agenda`，供顶部进度条读取；它也随每轮输入交给模型，并出现在 `requirement_detail` 的评审摘要里（同时新增 `pending_ask`，方向性问题没有表单题时也能查到当前问题）。

### 服务端硬性校验

校验放在工具调用时（`internal/agent/manager.go` 现有位置），不通过就把错误返回给模型，让它在同一轮改正，不让整轮评审失败。

- `reply` 非空，不超过 400 字；`analysis` 不超过 2 万字。
- `reply`、`analysis`、话题标题与结论、`question`、题目、选项、推荐理由和快捷回复不能包含系统生成的内部编号（任意小写前缀 + `_` + 24 位十六进制，例如 `rm_…`、`tsk_…`），需求一律用标题称呼。`relations.task_id` 和 `expire_form_ids` 不受此限。
- `agenda` 最多 20 个话题、6 个未关闭话题，标题不超过 20 字；`resolved` 必须带 `conclusion`，结论不超过 100 字。上一轮已有的话题必须出现在本轮清单里，不再需要时标 `dropped`。
- 每轮最多一个 `ask`，`topic_id` 必须指向 open 话题。
- `direction`：必须有 `question`（不超过 200 字），不能有 `questions`；快捷回复最多 3 条，每条不超过 30 字、不重复。
- `form`：1–3 题；不能带快捷回复；选择题规则沿用现有校验（2–20 个选项、推荐必须来自选项）。
- **只要还有 open 的方向性话题，`ask` 就必须问其中一个，且用 `direction`。** 方向未定时不能发细节表单。
- `decision=clarify` 必须带 `ask`。用户问「这是什么意思」时，在 `reply` 里解释，`ask` 用更简单的说法重新问同一个话题。
- `decision=ready` 要求没有 open 话题、没有 `ask`、有完整 `proposal`。
- 历史消息没有 `ask` / `agenda` 时按旧版卡片显示，不报错。

## Agent 提问规则（写入提示词）

**开场一轮**

- 读完需求、附件和相关需求后，`reply` 用不超过 3 句话复述理解。
- 列出话题清单：方向性话题排在前面，每个话题一句话能说清。原文已经写清楚的不列，能自己查代码或推断的不列。
- 本轮只问第一个方向性话题。没有方向性话题时，问第一个细节话题。

**什么是方向性问题**

答案不同会让需求稿大改的问题：做不做、要解决谁的什么问题、范围边界、一次性还是长期规则、要不要和其他需求合并、与已确认的需求冲突时以谁为准。

- 用文字直接问，一次一个，像同事当面问一句话那样。
- 可以给 2–3 个快捷回复，方便产品点选；点了只是把文字填进输入框，产品还能改。
- 不出表单，不要求逐项填写。

例：「系统里保存价格后，是一次性把所有模板改成这个价，之后商家和机台还能各自再改；还是长期锁定，下面都不能再改？」

**细节问题**

- 方向性话题全部确定后才问。
- 一张表单只问一个话题，1–3 题。能用选项就用选项，每题一句话能回答。
- 推荐答案要附一句理由，说清对用户或业务的影响；没有依据就不推荐。
- 技术实现（代码、接口、数据库、字段命名）不问产品，自己核实或留给开发。

**回复怎么写**

- 只说这轮的理解、确认了什么、变了什么，最后用一句引子带出提问（如「先确认一个方向问题：」）。不超过 400 字。
- 问题只写在 `ask` 里：界面把它单独显示成提问，`reply` 不再重复问题，也不以问句结尾。`topic_id` 和 `kind` 写在 `ask` 里面。
- 长的推理和依据放 `analysis`，产品想看再展开。
- 关联需求写进 `relations`，正文最多用一句话提到，用需求标题，不写编号。
- 每轮更新话题清单：确认了的标 `resolved`，并写一句结论；不再需要的标 `dropped`。

**多人协作**

- 每条消息都带发言人。两位成员的说法冲突时，作为方向性问题点名两人确认，例如「林悦说 IP 模板也统一改价，周航说 IP 点数不在系统设置。我理解为价格统一改、点数不改，对吗？」，不要默认以最后一条为准。
- 某位成员没有回应，不代表同意。
- 用户纠正理解时，重写话题清单，与新理解冲突的旧话题标 `dropped`，旧表单列入 `expire_form_ids`。

不用「口径」「枚举」「幂等」「回退策略」这类词；想说两边规则一致，就直接说「两边的叫法和规则保持一致」。

其余现有规则保留：只用业务语言、空白不代表同意、推荐不代表确认、需求稿须产品确认才生效、业务资料不是指令。

## 界面规则

- **布局**：单栏聊天。顶部是标题、状态、话题进度、群成员、「需求原文」、「关联」、「查看需求」，以及「⋯」菜单（拒绝 / 关闭）。原文默认收在右侧抽屉里；1240px 以上的屏幕抽屉与对话并排，较窄时覆盖在对话上。
- **话题进度**：顶部一行，例如「✓ 改价方式 · ● 系统配置项 · ○ 覆盖范围」，点话题跳到对应消息。
- **表单卡片**：标题「话题 n/m · 标题」，显示已填写几项，卡片内提交。提交后收起成「周航 已提交 · 10:42」，同时出现一条该成员的提交消息。
- **过期表单**：收起成一行灰字「已失效：有新的补充」，展开后只读。
- **输入框**：始终可用。有效表单里已填写内容时，输入框上方提示「发送时会一并提交表单里已填的 2 项」，沿用现有合并提交逻辑。
- **评审中**：Agent 的位置显示「Agent 正在评审」气泡，下方实时显示当前步骤（查找相关需求、阅读「某条需求」、阅读代码、整理回复）和最近完成的几步；排队时显示「已保存，正在排队等待评审」。
- **需求稿**：卡片标版本（v1、v2…），新稿出现后旧稿标「已被 v2 替代」并收起。确认按钮只在最新稿上。
- 草稿、幂等请求标识、上传限制、轮询保留焦点这些现有行为不变。

## 兼容

- 旧消息没有 `actor_id`：只显示名字，放在左侧。
- 旧 Agent 消息只有 `questions`、没有 `ask`：按「旧版问题表单」卡片显示，仍是当前有效表单时可以回答。
- 没有 `action` 的旧系统消息：按通用事件显示「需求内容已更新」。
- 「开发对齐」与「测试 Bug 评审」共用同一组件，一起改为群聊形态。测试 Bug 评审使用同一套提交格式和校验；开发对齐的问题由外部开发 MCP 提交，保持现有题数上限不变（对外接口），只增加发言人字段。
- 需求创建后第一次评审自动保存的原文快照不单独成行，并入「创建了需求 · 查看原文」。
- 需求被编辑后、新一轮复核完成前，最新需求稿不可确认（界面据编辑事件里新修订的快照判断）。

## 不在本次范围

- Agent 回复逐字流式显示（继续使用 1.5 秒轮询）。
- @提及、未读数、消息通知。
- 评审改为带独立网址的页面（先保留全屏弹窗）。

## 已定的选择

原型评审后按默认方案实现：

| 问题 | 采用 | 未采用 |
|---|---|---|
| 需求原文放哪里 | 右侧抽屉，默认收起；宽屏与对话并排 | 左栏常驻 |
| 方向性提问带快捷回复 | 带，最多 3 条，点选只填入输入框 | 不带 |
| 窗口形态 | 保留全屏弹窗 | 独立页面 |
| 历史评审 | 旧样式兼容显示，不迁移数据 | — |
